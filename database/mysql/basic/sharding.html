分表分库 ​

  • 是应对数据库性能瓶颈的核心方案，通过将数据分散到多个表或数据库中，解决单表 / 单库数据量过大导致的查询缓慢、写入瓶颈等问题。

为什么需要分表分库？ ​

  • 当数据库达到一定规模（如单表千万级以上），会面临以下问题：
    • 查询性能下降：索引树过大，扫描 / IO 成本高，即使走索引也可能变慢。
    • 写入压力大：单表写入并发高，锁竞争激烈（如行锁、表锁）。
    • 存储瓶颈：单库磁盘空间有限，备份 / 恢复耗时。
    • 扩展受限：单库无法利用多服务器资源，垂直扩展（升级硬件）成本高。

分库 ​

  • 分库是将一个数据库中的表切分成多个数据库（通常在不同服务器），每个数据库存储不同的表数据。
  • 分库的目的是将数据库的压力分散到多个数据库中，从而提高数据库的性能和吞吐量。
  • 示例：
    • 假设一个电商数据库包含用户表、订单表、商品表等。
      • 将用户表以及相关表 (如用户住址表、用户vip表等) 切分到一个数据库中，专门管理用户信息的。
      • 将商品表以及相关表（如商品属性表、商品分类表等）切分到一个数据库中，专门管理商品信息的。
      • 将订单表以及相关表（如订单信息表、订单商品表等）切分到一个数据库中，专门管理订单信息的。

分表 ​

  • 分表是将一个表中的记录切分到多个结构相同的表中。
  • 分表的目的是将表的数据分散到多个表中，从而提高表的查询性能和写入性能。
  • 示例：
    • 假设一个订单表包含了所有订单的信息，当订单量不断增加时，单表会变得非常庞大。
      • 可以将订单表按订单日期进行切分，每个月的订单数据存储在一个独立的表中，例如 order_202301、order_202302 等。
      • 每个月的订单表都可以独立进行查询和写入操作，避免了对单表的压力。

拆分策略 ​

水平切分 ​

  • 按行拆分，将表中不同行的数据分散到多个表 / 库，表结构不变。

范围拆分 ​

  • 按时间：如按月份分表：order_202301、order_202302；
  • 按ID分表：1-100万在表A，101-200万在表B
  • 优点：规则简单，便于扩容；
  • 缺点：可能存在数据倾斜，例如双11活动，订单集中这天。

哈希拆分 ​

  • 对关键字段（如用户 ID）哈希取模（如 user_id % 4 分为 4 个分片）。
  • 优点：数据分布均匀，避免热点；
  • 缺点：扩容需重新哈希（可通过一致性哈希缓解），历史数据迁移复杂。

列表拆分 ​

  • 按枚举值拆分（如按地区分表：order_beijing、order_shanghai）。
  • 优点：针对性优化（如地区业务隔离）；
  • 缺点：枚举值过多时分片数量爆炸。

组合拆分 ​

  • 结合多种规则（如先按范围分库，库内再按哈希分表）。

垂直切分 ​

  • 按列拆分，将表中不同字段拆分到不同表 / 库，通常按业务关联性拆分。
  • 将 “高频访问字段” 和 “低频 / 大字段” 分离。

示例 ​

  • 原表 user（含 id, name, age, avatar(大字段), description(长文本)）
  • 垂直切分后：
    • user_base（含 id, name, age）
    • user_detail（含 id, avatar, description）

优点 ​

  • 减少单表数据量，提升查询效率（高频表字段少，索引更高效）；
  • 隔离大字段 IO（如图片、长文本），避免影响核心业务。

缺点 ​

  • 多表关联查询变复杂（需跨表 join）；
  • 拆分过度会导致业务逻辑冗余。

实现方式 ​

客户端方案 ​

  • 在应用程序中直接处理分片逻辑（如路由、聚合），需开发人员手动实现。
  • 优点：简单直接，无需数据库支持；
  • 缺点：开发成本高，维护成本高（需手动处理分片逻辑）。

中间件方案 ​

  • 通过独立的中间件统一处理分片逻辑，对应用透明。

中间件 ​

  • ShardingSphere（国产，功能全面，支持分库分表、读写分离、分布式事务）；
  • MyCat（基于 Cobar，轻量级，适合中小规模）；
  • Vitess（谷歌开源，适合超大规模集群，支持 MySQL/PostgreSQL）。

工作原理 ​

  • 应用通过中间件访问数据库（如连接 ShardingSphere 的代理端口）；
  • 中间件解析 SQL，根据分片规则路由到目标表 / 库；
  • 汇总多分片结果，返回给应用。

优点 ​

  • 无业务侵入，规则动态配置，支持复杂场景（如跨分片 join）；

缺点 ​

  • 引入中间件开销，需额外维护。

关键挑战 ​

跨分片查询 ​

  • 问题：JOIN、GROUP BY、ORDER BY 涉及多分片时，性能差。
  • 方案：尽量避免跨分片查询；中间件支持分片键关联查询；预聚合结果（如用 ES 存储统计数据）。

分布式事务 ​

  • 问题：跨库操作需保证 ACID（如转账涉及两个库的账户表）。
  • 方案：采用最终一致性（如 TCC、SAGA 模式）；ShardingSphere 支持 XA/Seata 等分布式事务。

扩容与迁移 ​

  • 问题：分片数量不足时，需新增分片并迁移数据，避免服务中断。
  • 方案：提前规划分片数量（预留冗余）；使用中间件的在线扩容功能（如 ShardingSphere 的弹性伸缩）；双写迁移（旧分片写入时同步到新分片）。

全局 ID ​

  • 问题：分表后自增 ID 重复（单表自增无法保证全局唯一）。
  • 方案：UUID、雪花算法（Snowflake）、数据库号段模式（如 Leaf）、Redis 自增。

索引设计 ​

  • 问题：分片后索引仅在单分片内有效，全局索引维护难。
  • 方案：优先按分片键查询；非分片键查询可通过中间件路由到所有分片（性能差，需谨慎）；引入外部索引（如 ES）。

最佳实践 ​

  • 先优化，后拆分：单表未达瓶颈（如百万级）时，优先通过索引、SQL 优化、读写分离解决，避免过度设计。

  • 分片键选择：尽量使用高频查询的字段（如用户 ID、订单 ID），避免跨分片查询。

  • 控制分片粒度：分表数量不宜过多（如单库表数不超过 100），否则元数据管理复杂。

  • 数据倾斜监控：定期检查各分片数据量 / 访问量，避免热点分片（如某用户数据集中在一个分片）。

  • 备份与恢复：分库分表后，需针对每个分片单独备份，或使用工具统一管理（如 Percona XtraBackup）。
