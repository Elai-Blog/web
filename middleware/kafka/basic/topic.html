主题（Topic） ​

  • 简单来说就是消息的分类，每个消息都必须属于一个 Topic。

核心作用 ​

  • 消息的分类：按业务场景（如订单、日志、用户行为）拆分消息，避免数据混乱。
  • 解耦生产与消费：生产者只负责向 Topic 发消息，消费者只负责从 Topic 取消息，双方无需感知对方的部署位置或数量。
  • 支持多订阅：一个 Topic 可被多个消费者组（Consumer Group）同时订阅，实现 “一份消息，多端消费”（如 user-behavior 可同时被推荐系统、数据分析系统订阅）。

分区（Partition） ​

  • Topic 并非物理存储单元，其物理存储依赖 Partition（分区）—— 每个 Topic 会被划分为 1 个或多个 Partition，消息最终存储在 Partition 中。

分区的本质 ​

  • 物理存储单元：每个 Partition 对应磁盘上一个独立的目录（路径格式：{kafka-log-dir}/{topic-name}-{partition-index}），目录内包含多个 “日志分段文件（Log Segment）”，消息按顺序追加到 Log Segment 中。
  • 有序性保证：仅保证单个 Partition 内的消息有序（按发送时间 / 偏移量递增），但多个 Partition 之间无全局有序性（因消息会被轮询 / 按 key 分配到不同 Partition）。
  • 分布式扩展：Partition 可分散在 Kafka 集群的不同 Broker 节点上（例如 3 个 Broker、6 个 Partition 的 Topic，每个 Broker 可存储 2 个 Partition），实现存储和读写压力的分摊。

分区的分配逻辑 ​

  • 生产者发送消息时，Kafka 会根据配置的 分区策略 将消息分配到 Topic 的某个 Partition。
分区策略说明
轮询（默认）按顺序将消息依次分配到每个 Partition（如第 1 条→P0，第 2 条→P1，第 3 条→P0...）
key 哈希对消息的 key 计算哈希值，再对 Partition 数量取模，结果即为目标 Partition 索引
自定义分区器开发者可实现自定义分区逻辑，根据业务场景将消息分配到不同 Partition。

Topic关键属性 ​

属性名参数说明推荐值
分区数--partitions决定 Topic 的并行度（分区数越多，读写并行度越高）按峰值吞吐估算：
单 Partition 写入吞吐约 1000-5000 TPS，读取吞吐约 5000-10000 TPS；
例如峰值写入 10000 TPS，建议分区数 ≥ 2
副本数--replication-factor每个 Partition 的副本数量（含 Leader 副本），决定可用性（副本数越多，抗节点故障能力越强）生产环境建议 ≥ 2
（如 3 副本：1 Leader + 2 Follower，容忍 1 个节点故障）；
开发环境可设为 1
消息保留时间retention.ms消息在 Topic 中的保留时长，超时后会被自动删除（或按大小删除）按业务需求：日志类数据可设 7 天（604800000 ms），核心业务数据可设 30 天，或设为 -1 永久保留（需配合存储监控）
清理策略cleanup.policy消息过期后的处理方式- delete：删除过期消息（默认，适用于日志、行为数据）；
- compact：保留每个 key 最新的一条消息（适用于 “状态同步” 场景，如用户最新信息）

副本（Replica） ​

  • Kafka 通过 副本（Replica） 机制保证 Topic的高可用 —— 每个 Partition 有多个副本，其中 1 个为 Leader 副本，其余为 Follower 副本。

Leader 副本 ​

  • 唯一接收生产者的写入请求和消费者的读取请求；
  • 负责将新消息同步给所有 Follower 副本。

Follower 副本 ​

  • 被动同步 Leader 的消息（拉取 Leader 的日志数据），保持与 Leader 数据一致；
  • 当 Leader 副本所在 Broker 故障时，从 Isr 中选举新的 Leader，确保服务不中断。

故障恢复流程 ​

  • 当 Leader 副本所在 Broker 故障时，Kafka 会从 Isr 中选择一个 Follower 副本升级为新的 Leader。
  • 新的 Leader 副本会同步所有已提交的消息，确保数据一致性。
  • 其他 Follower 副本会从新的 Leader 副本拉取缺失的消息，保持与 Leader 一致。
  • 原 Leader 所在 Broker 重启后，会作为 Follower 向新 Leader 同步数据，重新加入 Isr。

主题操作 ​

创建主题 ​

bash
# 创建主题
kafka-topics.sh --create \
# 在哪些节点上加
--bootstrap-server broker1:9092,broker2:9092,broker3:9092 \
# 设置主题名称
--topic user-behavior \
# 设置分区3个
--partitions 3 \
# 设置副本数2个
--replication-factor 2 \
# 设置消息保留时间7天
--config retention.ms=604800000

查看主题 ​

bash
# 查看主题
kafka-topics.sh --list \
# 在哪些节点上查看
--bootstrap-server broker1:9092,broker2:9092,broker3:9092

# 查看主题详情
kafka-topics.sh --describe \
# 在哪些节点上查看
--bootstrap-server broker1:9092,broker2:9092,broker3:9092 \
# 查看主题的名称
--topic user-behavior

修改主题 ​

bash
# 修改主题
kafka-topics.sh --alter \
# 在哪些节点上修改
--bootstrap-server broker1:9092,broker2:9092,broker3:9092 \
# 修改主题的名称
--topic user-behavior \
# 修改分区数为4个
--partitions 4

删除主题 ​

bash
# 删除主题
kafka-topics.sh --delete \
# 在哪些节点上删除
--bootstrap-server broker1:9092,broker2:9092,broker3:9092 \
# 删除主题的名称
--topic user-behavior

go 代码示例 ​

  • 使用github.com/confluentinc/confluent-kafka-go/v2 库操作主题
go
func GetKafka() *kafka.AdminClient {
	client, err := kafka.NewAdminClient(&kafka.ConfigMap{
		"bootstrap.servers": "localhost:9092",
	})
	if err != nil {
		panic(fmt.Sprintf("连接kafka失败: %s", err))
	}
	return client
}

func main() {
	ctx := context.Background()
	client := GetKafka()
	// 创建主题
	topics, err := client.CreateTopics(ctx, []kafka.TopicSpecification{{
		Topic:             "test-3",
		NumPartitions:     5, // 设置5个分区
		ReplicationFactor: 1, // 1个副本,单机只能设置一个副本
		Config: map[string]string{
			"cleanup.policy": "delete",   // 删除策略
			"retention.ms":   "86400000", // 保存时间
		},
	}})
	defer client.Close()
	if err != nil {
		panic(fmt.Sprintf("创建主题失败: %s", err))
	}
	fmt.Println(topics)
	// 删除主题
	topics, err = client.DeleteTopics(ctx, []string{"test-2"})
	if err != nil {
		panic(fmt.Sprintf("删除主题失败: %s", err))
	}
	fmt.Println(topics)
}
