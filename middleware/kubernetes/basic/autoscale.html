自动伸缩 ​

  • K8s 伸缩分为Pod 水平伸缩 HPA、Pod 垂直伸缩 VPA、节点集群伸缩 CA、集群整体扩容 Cluster Autoscaler四层，外加事件驱动的 KEDA，覆盖从容器实例、资源配额到服务器节点全维度弹性。

伸缩类型 ​

组件伸缩对象作用适用场景
HPAPod 副本数增减 Pod 个数并发、CPU / 内存负载波动、流量起伏（最常用）
VPAPod CPU / 内存 request/limit调整单个 Pod 资源配额应用资源规格不合适、资源浪费 / OOM
CA集群 Node 节点增减云服务器节点所有 Pod 调度爆满、节点资源不足
KEDAHPA 增强基于消息、定时、外部指标伸缩队列堆积、定时任务、MQ、数据库延迟等业务指标

HPA 水平 Pod 自动扩容 ​

伸缩原理 ​

  • HPA 控制器周期性（默认 15s）从Metrics Server获取 Pod 监控指标（CPU、内存）
  • 公式：目标副本数 = 当前副本数 × (当前指标值 / 目标阈值)
  • 冷却窗口：扩容默认 3min、缩容默认 5min，防止抖动

前置依赖 ​

  • HPA 必须部署 Metrics Server（替代旧 Heapster）采集容器监控数据
yaml
# 部署metrics-server
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml
# 验证
kubectl top nodes
kubectl top pods

示例 ​

yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
    # 名称
    name: web-hpa
    namespace: default
spec:
    # 关联应用
    scaleTargetRef:
        apiVersion: apps/v1
        # 引用类型
        kind: Deployment
        # 应用名称
        name: web
    minReplicas: 2 # 最小副本
    maxReplicas: 10 # 最大副本
    behavior: # 自定义伸缩冷却策略
        scaleDown:
            stabilizationWindowSeconds: 300
        scaleUp:
            stabilizationWindowSeconds: 60
    metrics:
        - type: Resource
          resource:
              name: cpu
              target:
                  type: Utilization
                  averageUtilization: 70 # CPU使用率70%触发扩容
        - type: Resource
          resource:
              name: memory
              target:
                  type: Utilization
                  averageUtilization: 80 # 内存使用率80%触发扩容

指标类型 ​

  • 资源指标：CPU、内存（内置，最常用）
  • Pod 自定义指标：应用暴露的 Prometheus 业务指标（QPS、请求耗时）
  • 外部指标：MQ 队列长度、云监控、API 接口数据（配合 Prometheus Adapter）

VPA 垂直 Pod 自动伸缩 ​

作用 ​

  • 不增减 Pod 数量，自动修改 Pod 的resources.requests/limits，解决两类问题：
    • 资源给太大：节点资源空置浪费
    • 资源给太小：频繁 OOM、CPU 限流

三种模式 ​

  • Auto：推荐值 + 自动重启 Pod 更新资源（生产谨慎，会重建 Pod）
  • Recreate：资源不足时重建 Pod 扩容
  • OnlyRecommend：只输出推荐值，不修改 Pod（推荐生产使用）

警告 ​

  • VPA 不要和 HPA 同时管控 CPU / 内存指标，会互相冲突争抢调度。

CA 节点自动扩缩容 ​

  • 节点资源耗尽 → 新 Pod 处于Pending状态（调度失败）
  • CA 检测到 Pending Pod，调用云厂商 API（阿里云 / 腾讯云 / AWS）新增虚拟机节点
  • 节点空闲长时间（默认 10min 无高负载），CA 自动销毁闲置节点，节省成本

约束 ​

  • 仅支持云厂商托管 K8s（EKS/ACK/TKE），裸机集群无法使用 CA
  • 需要给 CA 授予云服务器的创建、删除权限

流程 ​

  • 用户流量上涨 → HPA 增加 Pod 副本 → 节点资源不够 → Pod pending → CA 新增节点 流量下降 → HPA 缩 Pod → 节点空闲 → CA 销毁多余节点

KEDA：事件驱动弹性（企业主流方案） ​

  • 原生 HPA 只支持 CPU / 内存，业务大多依赖消息队列、定时任务、数据库积压伸缩，KEDA 基于 HPA 做增强：

常用伸缩源 ​

  • RabbitMQ、Kafka、Redis List、MQTT、MySQL 慢查询、Cron 定时、Prometheus 指标、HTTP 负载

Redis 队列堆积自动扩容消费 Pod ​

  • 队列消息越多，消费 Pod 数量越多；消费完毕自动缩容至 0 副本（闲置时归零节省资源）
yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
    name: redis-consumer-scaler
spec:
    scaleTargetRef:
        name: consumer-deploy
    minReplicaCount: 0
    maxReplicaCount: 20
    triggers:
        - type: redis
          metadata:
              address: redis://redis-service:6379
              listName: task_queue
              listLength: 100 # 队列长度大于100开始扩容

避坑 ​

  • 必须配置 request+limit：没有 request，HPA 无法计算使用率
  • 配置伸缩冷却时间，避免流量毛刺造成频繁震荡扩容
  • 分层伸缩：HPA 负责 Pod 数、CA 负责节点、KEDA 对接业务指标
  • 缩容不要过于激进，搭配预热、会话粘连防止业务报错
  • 生产环境 VPA 优先使用OnlyRecommend，观测一段时间再手动优化资源
  • 配合监控告警：HPA 频繁扩容 / 缩容、节点新增销毁都配置告警
