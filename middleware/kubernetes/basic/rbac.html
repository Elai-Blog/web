权限管理 ​

  • K8s 默认采用 RBAC（基于角色的访问控制） 做权限管控

核心资源 ​

资源中文名称作用归属类型
User / ServiceAccount用户 / 服务账号身份主体，谁要访问集群主体（Subject）
Rule（Rules）权限规则定义：可以对哪些资源执行哪些操作权限细则
Role / ClusterRole角色 / 集群角色封装一组 Rules 权限集合权限载体
RoleBinding / ClusterRoleBinding角色绑定 / 集群绑定把「身份」和「角色权限」做关联授权关系

权限 ​

格式 ​

yaml
rules:
    # 核心资源只读
    - apiGroups: ['']
      resources: ['pods', 'services', 'configmaps']
      verbs: ['get', 'list', 'watch']
    # apps组资源只读
    - apiGroups: ['apps']
      resources: ['deployments', 'statefulsets']
      verbs: ['get', 'list', 'watch']

apiGroups ​

  • apiGroups: [""]：k8s 内置核心资源（pod、svc、cm、secret、deploy）
  • apiGroups: ["apps"]：deployment、statefulset、daemonset
  • apiGroups: ["rbac.authorization.k8s.io"]：RBAC 自身资源
  • apiGroups: ["networking.k8s.io"]：Ingress、NetworkPolicy

verbs ​

txt
# 只读
get, list, watch
# 修改
create, update, patch, delete, deletecollection
# 万能权限（慎用）
*

案例 ​

只读权限 ​

  1. 创建角色
yaml
apiVersion: v1
kind: ServiceAccount
metadata:
    name: user1
    namespace: rbac-demo
  1. 定义权限规则
yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
    name: readonly-role
    namespace: rbac-demo
rules:
    # 核心资源只读
    - apiGroups: ['']
      resources: ['pods', 'services', 'configmaps']
      verbs: ['get', 'list', 'watch']
    # apps组资源只读
    - apiGroups: ['apps']
      resources: ['deployments', 'statefulsets']
      verbs: ['get', 'list', 'watch']
  1. 给角色绑定权限
yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
    name: user1-role
    namespace: rbac-demo
# 绑定角色
subjects:
    - kind: ServiceAccount
      name: user1
      namespace: rbac-demo
# 绑定权限
roleRef:
    kind: Role
    name: readonly-role
    apiGroup: rbac.authorization.k8s.io
  1. 使用角色
yaml
apiVersion: v1
kind: Pod
metadata:
    name: rbac-pod
    namespace: rbac-demo
spec:
    # 使用角色
    serviceAccountName: user1
    containers:
        - name: curl-k8s
          image: curlimages/curl
          command: ['sleep', '36000']

集群级权限 ​

  1. 创建角色
yaml
apiVersion: v1
kind: ServiceAccount
metadata:
    name: user2
    namespace: rbac-demo
  1. 定义规则
yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
    name: cluster-global-read
rules:
    # 所有ns内基础资源只读
    - apiGroups: ['', 'apps', 'networking.k8s.io']
      resources: ['pods', 'services', 'deployments', 'ingresses', 'configmaps']
      verbs: ['get', 'list', 'watch']
    # 集群级别资源
    - apiGroups: ['']
      resources: ['nodes', 'persistentvolumes']
      verbs: ['get', 'list', 'watch']
    - apiGroups: ['storage.k8s.io']
      resources: ['storageclasses']
      verbs: ['get', 'list', 'watch']
  1. 给角色绑定权限
yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
    name: user2-role
subjects:
    - kind: ServiceAccount
      name: user2
      namespace: rbac-demo
roleRef:
    kind: ClusterRole
    name: cluster-global-read
    apiGroup: rbac.authorization.k8s.io

ClusterRole + RoleBinding ​

  1. 创建角色
yaml
apiVersion: v1
kind: ServiceAccount
metadata:
    name: user3
    namespace: rbac-demo
  1. 定义规则
yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
    name: cluster-global-read
rules:
    # 所有ns内基础资源只读
    - apiGroups: ['', 'apps', 'networking.k8s.io']
      resources: ['pods', 'services', 'deployments', 'ingresses', 'configmaps']
      verbs: ['get', 'list', 'watch']
    # 集群级别资源
    - apiGroups: ['']
      resources: ['nodes', 'persistentvolumes']
      verbs: ['get', 'list', 'watch']
    - apiGroups: ['storage.k8s.io']
      resources: ['storageclasses']
      verbs: ['get', 'list', 'watch']
  1. 给角色绑定权限
yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
    name: user2-role
subjects:
    - kind: User
      name: user3
roleRef:
    kind: ClusterRole
    name: cluster-global-read
    apiGroup: rbac.authorization.k8s.io

给外部开发用户颁发证书 + 绑定 RBAC 权限（日常运维最常用） ​

常用内置 ClusterRole（不用自己写规则） ​

  • k8s 自带一批开箱即用的 ClusterRole，生产优先使用
内置角色权限说明
cluster-admin集群最高管理员（全权限，等同于 root）
admin命名空间内完整管理权限（可删资源、配权限）
edit命名空间资源增删改，不能修改 RBAC、配额
view纯只读权限，不能修改任何资源

避坑 ​

  1. 最小权限原则：绝不随便使用verbs: ["*"]、cluster-admin
  2. 区分 SA 和 User：Pod 内部程序用 SA，人员登录使用证书 User
  3. 命名空间隔离：不同业务使用不同 ns，通过 Role 隔离权限
  4. Secret 权限严格管控：非必要不给任何人 get/list secret 权限
  5. 集群级资源（node/pv/crd）统一由运维通过 ClusterRole 管控
  6. 优先使用系统内置 view/edit/admin，减少自定义规则维护成本
  7. 定期清理无用 ServiceAccount、闲置证书、废弃 Binding
